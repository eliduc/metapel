# Спецификация: подписание табелей Битуах Леуми (יומן עבודה)

Дата: 2026-06-20. Статус: одобрен дизайн, ожидает проверки спецификации.
Приложение: «Выплаты метапелю» (PWA, ваниль ES5, GitHub Pages, репозиторий `eliduc/metapel`, данные в приватном `eliduc/metapel-data`).

## 1. Цель и контекст

Компания по уходу «Матав» каждый месяц присылает Григорию PDF-табель (יומן עבודה / «журнал работы») для Битуах Леуми с уже проставленными часами. Этот табель должен подписать **метапель** (Джамшид — в каждой строке с часами, недельную подпись и подтверждение внизу) и **член семьи** за Григория (нижний блок). После подписания семья скачивает PDF, отправляет письмом в Матав и отмечает «Отослано».

Сейчас это делается на бумаге. Цель — новый раздел приложения **«Табели»**: загрузка присланного PDF, подписание пальцем (с авто-расстановкой подписей по местам бланка), хранение в общей БД (синхронно на всех устройствах), статусы, скачивание, отметка «Отослано».

## 2. Объём

**В объёме:**
- Вкладка «Табели» с красным бейджем числа «подписан, но не отослано».
- Загрузка PDF (iPad и лэптоп) в БД на сервере; видимость на всех устройствах со статусами.
- Подписание: кнопки «Подписать Метапелет» и «Подпись Григория», чекбокс «Все подписи» (по умолч. включён).
- Авто-расстановка подписей по PDF Матав (строки с часами, недельные ячейки, нижние блоки) + предпросмотр перед сохранением.
- Статусы: не подписан → подписан метапелем / подписан Григорием → полностью подписан → отослано.
- Скачивание подписанного PDF (доступно, как только подписан хотя бы одним).
- Отметка «Отослано» (чекбокс, ставит пользователь вручную).

**Вне объёма (YAGNI):**
- Автоматическая отправка e-mail (приложение статическое, без бэкенда; письмо отправляет пользователь сам).
- Генерация бланка «с нуля» (работаем строго с присланным PDF Матав).
- Изменение/удаление часов в табеле (часы приходят от Матав, не редактируем).
- Поддержка сканов-картинок (PDF от Матав текстовый; для сканов парсинг невозможен — см. риски).
- Кнопка «Отослать повторно» (не нужна — статус «Отослано» переключается отметкой).

## 3. Точка входа и навигация

- Новая, **5-я вкладка** в `nav`: `data-tab="timesheets"`, подпись «📋 Табели».
- На вкладке — **красный бейдж** (как `#badge-due`) с числом табелей в статусе «полностью подписан, но не отослано». Виден из любой вкладки, в т.ч. с главной «Платить».
- `renderTimesheets(content)` — рендер списка (аналогично `renderHistory`/`renderAdvance`).

## 4. Модель данных и хранение

### 4.1. Запись табеля (в синхронизируемой БД)
Хранится в `localStorage` и в облачном бэкапе `backup/data.json` новым массивом `timesheets`:

```
{
  id: 'ts-' + Date.now(),
  month: '2026-06',            // период из имени/контента (или выбран при загрузке)
  fileName: 'יומן עבודה 06-2026.pdf',
  uploadedDate: '2026-06-20',
  caregiverSigned: false,      // подписал метапель
  caregiverSignedDate: null,
  familySigned: false,         // подписал член семьи (за Григория)
  familySignedDate: null,
  sentMarked: false,           // отмечено «Отослано»
  sentDate: null
}
```

**Статус — вычисляемый** из флагов (НЕ хранится отдельно, чтобы не рассинхронизироваться):
- `sentMarked` → «отослано»;
- иначе `caregiverSigned && familySigned` → «полностью подписан»;
- иначе `caregiverSigned` → «подписан метапелем»;
- иначе `familySigned` → «подписан Григорием»;
- иначе → «не подписан».

### 4.2. Файлы PDF (в репозитории `metapel-data`)
- Исходный (как загружен): `<dataPrefix>timesheets/<id>.json` — JSON `{ pdf: 'data:application/pdf;base64,...', fileName, month }` (по аналогии с `receipts/<id>.json`; единый механизм чтения/записи `putFile`/`fetchReceipt`).
- Подписанный: `<dataPrefix>timesheets/<id>-signed.json` — создаётся/обновляется при каждом подписании.
- `dataPrefix` (`''`/`stage/`) — как у расписок, среды изолированы.

Размер: один табель ≈ 150 КБ (base64 ≈ 200 КБ < 1 МБ лимита Contents API на чтение). Хранение PDF в `localStorage` — тяжёлое; поэтому **PDF в localStorage не держим**, тянем по запросу из репо (как расписки через `fetchReceipt`). В синхронизируемой БД — только лёгкие метаданные (запись из 4.1).

### 4.3. Синхронизация
- Метаданные (`timesheets[]`) синхронизируются существующим механизмом (`backup/data.json`, авто-pull/push). `buildBackupObject`/`buildBackupJson` добавляют поле `timesheets: store.loadTimesheets()`. Поэтому загруженный на лэптопе табель и его статус видны на iPad и наоборот.
- `localSupersedesCloud` / merge: массив `timesheets` добавляется к проверкам состава (по `id`) — не теряем и не воскрешаем (та же логика, что для log/extras/returns).
- `replaceData` (restore) и `lightenRecord` учитывают `timesheets` (PDF в метаданных не лежит — облегчать нечего, но проверить, что массив не теряется при restore).

## 5. Загрузка табеля

- Кнопка «Загрузить табель» → `<input type="file" accept="application/pdf">` (iPad: «Файлы»; лэптоп: проводник).
- Файл читается `FileReader` → base64; месяц определяется из контента PDF (период `MM/YYYY` в шапке) или, если не распознан, спрашивается у пользователя.
- Запись добавляется в `timesheets[]` (статус «не подписан»), исходный PDF заливается в `timesheets/<id>.json`, запускается `runSync` (донести метаданные в облако).
- Работает на обоих устройствах (токен архива уже введён).

## 6. Подписание

### 6.1. Кнопки и чекбоксы (в карточке табеля)
- «Подписать Метапелет» + чекбокс **«Все подписи»** (по умолч. включён).
- «Подпись Григория» + чекбокс **«Все подписи»** (по умолч. включён).
- Кнопка показывается, пока соответствующий подписант ещё не подписал.

### 6.2. Окно подписи
Переиспользуется существующая площадка подписи пальцем (`#modal-sign` / `setupSignCanvas`): canvas + «ОК».

- **Чекбокс «Все подписи» включён:** окно открывается **один раз**; нарисованная подпись ставится **во все места** этого подписанта.
- **Чекбокс выключен:** окно открывается **по разу на каждое место**; над площадкой — надпись «за что» (напр. «За вторник 16 июня», «Недельная подпись — неделя 2», «Подтверждение метапеля», «Подпись семьи за Григория»); подписант расписывается каждый раз.

### 6.3. Места подписей (что куда)
| Подписант | Места |
|---|---|
| Метапель | каждая строка с проставленными часами (столбец `חתימת המטפלת`) |
| Метапель | недельная подпись (`חתימה שבועית`) — по одной на неделю с рабочими днями |
| Метапель | подтверждение внизу `אישור המטפל/ת`: подпись + имя (`workerFullName`) + дата (сегодня) |
| Семья (Григорий) | нижний блок `בן/בת משפחה`: подпись (+ при необходимости «קרבה» из настроек) |
| Компания `אישור החברה` | **не трогаем** |

### 6.4. Авто-расстановка (определение мест)
- PDF парсится через **pdf.js**: для каждой страницы извлекаются текстовые элементы с координатами (x, y, w, h).
- Якоримся на постоянные ивритские заголовки шаблона Матав:
  - столбцы `כניסה`/`יציאה`/`סה״כ שעות` → определяют x-диапазон «часов»; строка «с часами» = в её диапазоне есть значения времени/числа.
  - заголовки `חתימת המטפלת` и `חתימה שבועית` → x-позиции столбцов подписи.
  - блоки `אישור המטפל/ת`, `בן/בת משפחה` (и их подписи/имена/даты) → координаты нижних блоков.
- По строкам с часами и неделям формируется список «слотов» (каждый: тип, координаты, надпись).
- Подписи (PNG) и текст (имя/дата) штампуются в координаты через **pdf-lib**; результат — подписанный PDF.

### 6.5. Предпросмотр (обязателен)
Перед сохранением показывается отрендеренный (pdf.js) подписанный PDF — пользователь видит, куда легли подписи, и подтверждает «Сохранить» либо «Отмена». Это страховка от «подпись уехала» в госдокументе.

### 6.6. Накопление и сохранение
- Подписи накапливаются: метапель подписал → `…-signed.json` (на базе исходного); семья подписала → штампуем поверх текущего подписанного.
- После подтверждения: подписанный PDF заливается в репо, в записи ставится `caregiverSigned`/`familySigned` = true + дата, `runSync`.
- Повторное подписание тем же подписантом в v1 не предусмотрено (подписал — кнопка скрывается). Если ошибка — перезагрузить исходный PDF новой записью.

## 7. Статусы, скачивание, «Отослано»

- **Скачать PDF** — доступно, как только подписан **хотя бы одним** подписантом (отдаёт текущий подписанный PDF). Скачивание: `Blob` + `<a download>` (iPad/лэптоп).
- **«Отослано»** — чекбокс в карточке; пользователь ставит сам после отправки письма. Ставит `sentMarked=true`, `sentDate`, `runSync`. Снять отметку можно (вернёт в «полностью подписан»).
- Бейдж на вкладке = число записей `полностью подписан && !sentMarked`.

## 8. Технические решения и зависимости

- **pdf.js** (рендер + извлечение текста с координатами) и **pdf-lib** (штамповка изображений/текста, экспорт PDF). Обе **встраиваются в репозиторий** (`js/vendor/`), добавляются в `SHELL` service worker — чтобы автономность/офлайн приложения сохранились (без зависимости от CDN). pdf.js worker — тоже локально.
- Размер: ≈ 1.5 МБ суммарно; кэшируется SW; грузится только при заходе в раздел (ленивая загрузка скриптов, чтобы не тормозить основное приложение).
- Подпись пальцем — существующий canvas-механизм, без изменений.
- Среды prod/stage изолированы (`dataPrefix`, ключ хранилища) — как уже сделано.

## 9. Этапы реализации

- **Этап 1 — каркас раздела:** вкладка «Табели», загрузка PDF, хранение в репо + синхронизация метаданных, список со статусами (пока только «не подписан»), бейдж. (Без подписи; скачивание появляется на Этапе 2, т.к. скачивать можно только подписанные.) Включить `timesheets` в merge/restore/sync (`buildBackupObject`, `replaceData`, `localSupersedesCloud`).
- **Этап 2 — подписание:** pdf.js/pdf-lib (vendored), парсинг шаблона Матав (калибровка по реальному `2026.pdf`), две кнопки + чекбокс «Все подписи», авто-расстановка, предпросмотр, сохранение подписанного PDF, продвижение статусов.
- **Этап 3 — завершение:** отметка «Отослано», бейдж по неотосланным, скачивание подписанного, полировка, запасной ручной режим правки позиций (если предпросмотр показал смещение).

Каждый этап: сначала **staging**, тесты, затем прод. Отдельная адверсариальная проверка синхронизации `timesheets` (как делали для расписок — не потерять/не воскресить/не затереть).

## 10. Тестирование и верификация

- Юнит-тесты (`test.html`): вычисление статуса из флагов; включение `timesheets` в `localSupersedesCloud` (состав, не воскрешать удалённые, не терять); парсер слотов на реальном `2026.pdf` (ожидаемое число слотов = число строк с часами + число недель + 2 нижних).
- Браузер (мок): загрузка PDF → запись/статус; подписание «Все подписи» → подписи во всех слотах; индивидуальный режим → N окон; предпросмотр; скачивание; отметка «Отослано»; бейдж.
- Калибровка парсера на присланном файле Григория; визуальная проверка предпросмотра.

## 11. Риски и компромиссы

- **Авто-расстановка — главный риск.** Зависит от стабильности шаблона Матав (текстовый PDF, постоянные заголовки). Митигация: якоримся на ивритские заголовки (устойчиво к разным комиссиям/расписаниям), **обязательный предпросмотр**, запасной ручной режим правки позиций (Этап 3).
- **Скан вместо текста:** если Матав однажды пришлёт скан-картинку, парсинг невозможен → показать понятную ошибку и предложить ручной режим/бумагу.
- **Размер репо:** ~150 КБ/мес PDF — за годы немного; приемлемо.
- **Лимит Contents API 1 МБ на чтение:** один табель < 1 МБ; ок. Если подписанный раздуется (много PNG-подписей) — оптимизировать подпись (ужать PNG/один экземпляр на все слоты).
